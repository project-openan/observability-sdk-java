# 业务指标视图

本文档将《[信号目录](信号目录.md)》记录的原始观测信号组织为业务可读的指标：每项给出计算方式（PromQL 示意）、来源信号与获取方式，并按四层递进组织，上层指标异常时逐层下钻定位根因。

**计算原则**：SDK 只按 YAML 声明记录原始事实（Counter、Histogram、Span、Log）；比率、分位数、排行等派生指标一律在存储 / 查询后端计算。比率不可跨实例 / 维度再聚合（Counter / Histogram 才可加），口径变更只需修改后端查询，无需 SDK 发版。

**计算位置**（本仓库 `deploy/local-storage/` 栈）：Prometheus/Thanos 计算 Metric，Jaeger 计算 Trace，OpenSearch 计算 Log。公式中指标名使用短名示意；Prometheus 序列名为 OTel 全名（Counter 另带 `_total` 后缀），例如 `workflow.count` → `gen_ai.agent.a2at.workflow.count_total`。窗口与分母口径（如是否含 `cancelled`）由看板 / 告警规则定义。

## 递进结构

```
L1 业务成果 ── 业务成功率 · E2E 处理时长 · 业务吞吐
              ↓ 成功率下降 / 时长劣化
L2 协作质量 ── 任务 · 协商 · 授权 · 通知成功率 · A2A 操作错误率
              ↓ 定位到某类协作环节
L3 执行质量 ── 步骤 / 子步骤失败率与耗时 · 最慢环节 · Agent 活跃
              ↓ 归因到具体环节
L4 资源消耗 ── Token 各级分布 · 单位任务 / 工作流成本 · 输出效率
```

## L1 业务成果层

| 业务指标 | 计算方式（示例） | 来源信号 | 获取方式 |
|---|---|---|---|
| 业务成功率 | `rate(workflow.count{workflow.status="completed"}) ÷ rate(workflow.count)`，按 `workflow.type` 分组 | `workflow.count` | 比率聚合 |
| E2E 处理时长 | `histogram_quantile(0.95, rate(workflow.duration_bucket[5m]))` | `workflow.duration` | 分位数聚合 |
| 业务吞吐量 | `rate(workflow.count[5m])`，按 `workflow.type` | `workflow.count` | 直读 |

## L2 协作质量层

| 业务指标 | 计算方式（示例） | 来源信号 | 获取方式 |
|---|---|---|---|
| 任务成功率 | `rate(task.count{task.status="completed"}) ÷ rate(task.count)`，按 `task.type` | `task.count` | 比率聚合 |
| 任务耗时分布 | `histogram_quantile(0.95, rate(task.duration_bucket[5m]))`，可按 `task.status` 拆分 | `task.duration` | 分位数聚合 |
| 协商成功率 | `rate(negotiation.count{negotiation.result="accepted"}) ÷ rate(negotiation.count)` | `negotiation.count` | 比率聚合 |
| 协商轮数 | `histogram_quantile(0.95, rate(negotiation.rounds_bucket[5m]))` | `negotiation.rounds` | 分位数聚合 |
| 授权通过率 | `rate(authorization.preauthorize.count{authorization.result="allowed"}) ÷ rate(authorization.preauthorize.count)` | `authorization.preauthorize.count` | 比率聚合 |
| 通知送达率 | `rate(notification.count{notification.result="sent"}) ÷ rate(notification.count)`，按 `notification.topic` | `notification.count` | 比率聚合 |
| A2A 操作错误率 | `Σ rate(operation.duration_count{error.type!=""}) ÷ Σ rate(operation.duration_count)`，按 `operation.name` | `gen_ai.client.operation.duration` | 比率聚合（`error.type` 仅出错时出现） |
| 流式调用错误率 | 同上 | `gen_ai.agent.a2a.streaming.duration` | 比率聚合 |
| 推送失败率 | 带 `error.type` 的 Span 占比 | `SendPushNotification` | Trace 聚合 |

## L3 执行质量层

| 业务指标 | 计算方式（示例） | 来源信号 | 获取方式 |
|---|---|---|---|
| 步骤失败率 | `rate(step.count{workflow.step.status="failed"}) ÷ rate(step.count)`，按 `gen_ai.agent.name` | `step.count` | 比率聚合 |
| 步骤耗时分布 | `histogram_quantile(0.95, rate(step.duration_bucket[5m]))`，按 Agent | `step.duration` | 分位数聚合 |
| 子步骤失败率 / 耗时 | 同上，`substep.count` / `substep.duration` 按 Agent | `substep.count` / `substep.duration` | 比率 / 分位数聚合 |
| 最慢步骤排行 | 按 Span 名聚合 `step.<name>` 的时长 p95 | `step.*` Trace | Trace 聚合 |
| 流式首事件时延 | 流式父 Span 起点到首个 `-event` Span 起点的时间差（按 Span Link 关联） | `SendStreamingMessage` / `-event` Trace | Trace 聚合 |
| Agent 活跃数 | `agent.state`＝running 去重计数 | `agent` Log | Log 聚合 |

## L4 资源消耗层

| 业务指标 | 计算方式（示例） | 来源信号 | 获取方式 |
|---|---|---|---|
| Token 总消耗 | `rate(input_tokens) + rate(output_tokens)` | `gen_ai.client.inference.usage.*` | 直读 |
| Token 各级分布 | 同上按 `gen_ai.provider.name` / `gen_ai.request.model` / `gen_ai.token.modality` / `gen_ai.agent.name` / `gen_ai.operation.name` 分组 | 同上（按 Agent 需传可选维度） | 直读分组 |
| 每任务 token 成本 | `Σ rate(tokens) ÷ rate(task.count)`，按 `task.type` | Token 指标 ÷ `task.count` | 跨指标比率 |
| 每工作流 token 成本 | `Σ rate(tokens) ÷ rate(workflow.count)` | Token 指标 ÷ `workflow.count` | 跨指标比率 |
| 平均每调用 token | `Σ rate(tokens) ÷ Σ rate(operation.duration_count)` | Token 指标 ÷ 操作计数 | 跨指标比率 |
| 输出效率 | `rate(output_tokens) ÷ rate(input_tokens)` | Token 指标 | 比率聚合 |
| 按调用 / 任务归因 token | 按 `task_id` 汇总 Span 的 `usage.input_tokens` / `usage.output_tokens` | A2A 协议 Span | Trace 聚合 |

## 获取方式说明

| 获取方式 | 执行位置 | 说明 |
|---|---|---|
| 直读 / 直读分组 | Prometheus | 直接读取 Counter / Histogram 序列，按维度分组 |
| 比率聚合 | Prometheus | 同源两个序列相除（如 completed ÷ total） |
| 分位数聚合 | Prometheus | `histogram_quantile` 对 `_bucket` 序列计算 p50 / p95 / p99 |
| 跨指标比率 | Prometheus | 不同指标序列相除，时间窗由后端对齐 |
| Trace 聚合 | Jaeger | 按 Span 属性过滤统计、按 Span 名聚合时长、按 Span Link / `task_id` 关联 |
| Log 聚合 | OpenSearch | 按日志事件与属性过滤、去重计数 |

## 层间下钻联动

- **指标 → Trace**：直方图类 Metric 通过 Prometheus Exemplar 携带 `trace_id` / `span_id`，可从指标样本直接下钻对应 Trace（`deploy/local-storage/` 已启用）。
- **跨信号关联**：同一执行以 `workflow.id` / `workflow.step.id` / `task_id` 串联 Metric、Trace、Log。
- **典型递进诊断路径**：业务成功率下降（L1）→ 某类 `task.type` 失败率高（L2）→ 失败集中在某 Agent 的步骤（L3）→ Exemplar 下钻该 Span，确认其 token 消耗与耗时是否异常（L4）。
